# الأمر الاحترافي الكامل: إصلاح وتطوير تطبيق «إدارة مخزون» (استوديو فوتوسيشن)

> **طريقة الاستخدام:** ارفع مع الأمر ده ملفات المشروع (النسخة 7 هي الأساس). انسخ كل اللي تحت الخط وابعته. لو الأداة بتحدّ طول الرسالة، ابعته على أجزاء بالترتيب (الأجزاء مرقمة) وقول للذكاء الاصطناعي «استنى لحد ما أقولك خلصت».
> **ممنوع** تلصق في الأمر أو في الشات أي باسورد أو رابط MongoDB حقيقي. الأسرار بتتحط في ملف `.env` على السيرفر بس.

## الجزء 0: التعريف والقواعد الحاكمة

أنت مهندس Full-Stack كبير (Node.js / TypeScript / MongoDB / أمان تطبيقات ويب / واجهات عربية RTL).
قدامك مشروع تطبيق **«إدارة مخزون»** لاستوديو تصوير ومعمل طباعة وتجليد ألبومات في مصر اسمه **«فوتوسيشن»**.
المشروع اتولّد بأداة AI Studio في عدة نسخ، **النسخة 7 هي الأحدث والأساس**. فيها ميزات كويسة وأخطاء أمنية وبرمجية خطيرة. مهمتك: تطلّع نسخة نهائية آمنة وثابتة ونظيفة، من غير ما تفقد الميزات الكويسة.

**قواعد العمل (إلزامية):**
1. **ما تخمّنش.** أي حاجة ناقصة أو متعارضة: اسألني قبل ما تكمّل. ما تخترعش أسماء موردين أو أرقام تليفونات أو أي بيانات حقيقية.
2. **اشتغل على مراحل** (موضحة في الجزء 13). بعد كل مرحلة شغّل الاختبارات وقولي إيه اللي اتعمل بالظبط.
3. **لكل تعديل**: قولي الملف والدالة اللي اتغيرت، وليه، وإزاي تتأكد إنه اشتغل.
4. **ما تحطّش أي سر** (PIN، باسورد، مفتاح API، رابط قاعدة بيانات) في أي ملف في المشروع. أسرار = متغيرات بيئة فقط.
5. **اتبع التعليمات دي حرفياً** حتى لو الكود الحالي بيعمل عكسها. لو لقيت تعارض اذكره لي.
6. **شرح للمبتدئ:** أنا مش مبرمج. في آخر كل مرحلة اشرح لي بلغة بسيطة (3–6 سطور) إيه اللي اتغير وإيه اللي المفروض أجربه بإيدي.

## الجزء 1: وصف التطبيق (علشان تفهم الغرض)

**المبدأ الأساسي «صفر فلوس»:** التطبيق كميات وجاهزية فقط. ممنوع أي سعر أو تكلفة أو عملة في أي مكان (واجهة، قاعدة بيانات، تقارير، واتساب، برومبت Gemini). لو لقيت أي حاجة بخصوص السعر امسحها.

**الأدوار:**
- **واجهة المالك:** عرض فقط، من غير دخول.
- **واجهة المدير:** محمية بـ PIN، فيها كل التعديل. زر الدخول شفاف وهادي في ركن الشاشة.

**واجهة المالك:** بانر إشارة المرور (🟢 مستقر / 🟠 تنبيه / 🔴 خطر)، 4 كروت إحصائيات (الجاهزية للتسليم، مؤشر الاستقرار، أصناف تحتاج انتباه، إجمالي الأصناف)، شبكة قدرة الإنتاج مع «عنق الزجاجة»، صندوق الأصناف العاجلة، جدول المخزون ببحث وفلاتر، زر مشاركة واتساب، زر استشارة الذكاء الاصطناعي.

**واجهة المدير (تبويبات):** الأصناف (إضافة/تعديل/أرشفة/حذف/حركة سريعة)، قوالب الشغل (تنفيذ بمضاعف يخصم الخامات)، الحركات (سجل وتراجع)، الجرد الفعلي، الذكاء الاصطناعي (تحليل استهلاك + تقرير Gemini)، الإعدادات.

**الملفات الحالية:** `server.ts` (Express + MongoDB + Gemini)، `inventory_logic.ts` (دوال حسابية نقية)، `inventory_logic.test.ts`، `index.html` (واجهة كاملة وجافاسكريبت في ملف واحد حوالي 178KB)، `sw.js`، `manifest.json`، `data-store.json`.

## الجزء 2: الأخطاء الأمنية الحرجة (الأولوية القصوى) — اشرح وصلّح كل واحدة

### الخطأ 1: الـ PIN الرئيسي (MASTER_PIN) مكتوب في الكود وظاهر للزوار
**المكان:**
- `server.ts`: السطرين `DEFAULT_PIN` و`MASTER_PIN` (حوالي 77–78)، ودالة `verify-pin` (حوالي 399–410) و`change-pin` (حوالي 415–435).
- `index.html`: `const MASTER_PIN` (حوالي 1948) وكائن الحالة الافتراضي `pin:` (حوالي 1952)، والتحقق في `verifyAndSubmitPin` (حوالي 3361)، ودالة تغيير الـ PIN (حوالي 3639)، وفقرة «الرمز المعتمد لفتح واجهة المسؤول» في الإعدادات (حوالي 1478)، وحقل `placeholder` للـ PIN الحالي (حوالي 1482)، وفي نافذة الدخول سطر يعرض الرمز (حوالي 1654) وحقل `placeholder` (حوالي 1660)، وزر `btn-quick-fill-pin` (حوالي 1652) اللي بيكتب الرمز تلقائياً، ورسائل خطأ بتذكر الرمز.
- `data-store.json`: فيه `"pin"` مخزّن نص عادي.

**ليه ده خطر:** أي زائر يفتح الصفحة يشوف الرمز أو يضغط «تعبئة سريعة» ويدخل واجهة المدير. وكمان الرمز مفتاح رئيسي: حتى لو المدير غيّر الـ PIN، الرمز القديم لسه شغّال. وبما إن الرمز اتنشر في الكود والمحادثات لازم يعتبر مكشوف نهائياً.

**الحل خطوة بخطوة:**
1. ابحث في كل ملفات المشروع عن: `MASTER_PIN` و`DEFAULT_PIN` و`btn-quick-fill-pin` وأي رقم من 11 خانة يبدأ بـ 01 (رقم موبايل). **امسح كل ظهور** من الكود والواجهة والتعليقات ورسائل الخطأ والـ placeholders ومن `data-store.json`.
2. السيرفر **لا يخزّن PIN نص عادي أبداً.** خزّن `pin_hash` + `salt` فقط، باستخدام `crypto.scrypt` (مدمج في Node):
```ts
import crypto from 'crypto';
function hashPin(pin: string, salt = crypto.randomBytes(16).toString('hex')) {
  const hash = crypto.scryptSync(pin, salt, 64).toString('hex');
  return { salt, hash };
}
function verifyPin(pin: string, salt: string, hash: string) {
  const test = crypto.scryptSync(pin, salt, 64);
  const stored = Buffer.from(hash, 'hex');
  return stored.length === test.length && crypto.timingSafeEqual(stored, test);
}
```
3. أول تشغيل: لو مفيش مستند `admin_auth` في قاعدة البيانات، أنشئه من متغير البيئة `INITIAL_ADMIN_PIN` (إجباري، 6 أرقام على الأقل، وارفض تشغيل السيرفر في الإنتاج لو مش موجود أو لو بسيط زي `123456` أو `000000`). حط `must_change_pin: true`.
4. عند أول دخول ناجح و`must_change_pin = true`: الواجهة تجبر المدير يغيّر الـ PIN قبل أي شاشة تانية.
5. شيل أي مقارنة بين الـ PIN و«رمز رئيسي». في مقارنة واحدة بس: `verifyPin(input, salt, hash)`.
6. **ما تبعتش الـ PIN أو الـ hash للمتصفح في أي رد API.** شيل `pin` من `getFullData()` ومن كل الردود.
7. **الواجهة:** نافذة الدخول تشيل أي إشارة للرمز، وتشيل زر التعبئة السريعة، وتشيل نص «الرمز المعتمد». رسالة الخطأ الوحيدة: «الرمز غير صحيح».
8. الرمز: 6 أرقام بالظبط (أرقام فقط). اقبل الأرقام العربية الهندية (٠–٩) وحوّلها لإنجليزية قبل الإرسال. استخدم الـ 6 خانات المنفصلة مع لوحة الأرقام (انظر الجزء 5، البند 1) بدل الحقل الواحد الطويل.

**اختبار القبول:** `grep -rn "MASTER_PIN\|quick-fill\|01[0-9]\{9\}" .` ما يرجعش حاجة. فتح DevTools > Network والتجول في كل الشاشات: ما يظهرش أي PIN في أي رد.

### الخطأ 2: دخول المدير بعلامة في المتصفح (localStorage)
**المكان:** `index.html` حوالي السطور 3306 و3385 و3410: `localStorage.getItem('admin_logged_in') === 'true'`.
**ليه ده خطر:** أي حد يفتح Console ويكتب `localStorage.setItem('admin_logged_in','true')` فيبان له زر/واجهة المدير. والأهم إن السيرفر نفسه ما بيتحقق من أي حاجة، فمفيش حماية حقيقية.

**الحل:**
1. `POST /api/auth/login` يستقبل `{ pin }`، يتحقق في السيرفر، ويرجّع كوكي جلسة: `HttpOnly; Secure (في الإنتاج); SameSite=Strict; Path=/; Max-Age=43200` (12 ساعة).
2. استخدم جلسة موقّعة: ولّد توكن عشوائي 32 بايت، خزّن hash منه في مجموعة `sessions` في MongoDB مع `expires_at` (واعمل TTL index)، أو استخدم JWT موقّع بـ `SESSION_SECRET`. اختار الأبسط والأوضح.
3. اعمل middleware اسمه `requireManager` يقرأ الكوكي ويتحقق، ويرجع `401` لو غير صالح. طبّقه على **كل** نقاط التعديل (انظر جدول الجزء 3).
4. `GET /api/auth/me` يرجع `{ isManager: true/false }`. الواجهة تعتمد عليه عند فتح التطبيق، **مش** على localStorage. امسح كل استخدام لـ `admin_logged_in`.
5. `POST /api/auth/logout` يمسح الجلسة والكوكي. زر «قفل وضع المدير» يستدعيه.
6. استخدم حزمة `cookie-parser`، وفي الإنتاج `app.set('trust proxy', 1)` لو السيرفر ورا proxy.

**اختبار القبول:** بعد `localStorage.setItem('admin_logged_in','true')` يدويًا، أي طلب تعديل (مثلاً إضافة صنف) بيرجع 401 وواجهة المدير ما تفتحش.

### الخطأ 3: `POST /api/db/connect` من غير حماية (جديد في النسخة 7)
**المكان:** `server.ts` حوالي السطر 308.
**ليه ده خطر:** أي زائر يقدر يبعت رابط MongoDB بتاعه، فالسيرفر يبدّل قاعدة البيانات ويكتب بيانات الاستوديو عليها (أو يقرأ منها بيانات مزيفة). كمان الرابط (فيه باسورد) بيتخزن في `settings.mongo_uri` ويتحفظ في `data-store.json` ويتبعت لأي زائر ضمن الإعدادات.

**الحل:**
1. **احذف نقطة `/api/db/connect` بالكامل** ودالة `connectMongoWithUri` المرتبطة بتغيير القاعدة وقت التشغيل.
2. **احذف من الواجهة** خانة `set-mongo-uri` وزر `btn-connect-mongodb` وكل معالجاتهم (حوالي 1530، 1537، 3681–3720).
3. **احذف** حقل `mongo_uri` من الإعدادات ومن `DEFAULT_SETTINGS` ومن كل مكان.
4. الاتصال بقاعدة البيانات يحصل **مرة واحدة عند تشغيل السيرفر** من `process.env.MONGODB_URI` فقط. لو فشل في الإنتاج: السيرفر يوقف ويطبع رسالة واضحة (مش بيعمل fallback صامت لملف محلي).
5. اترك لوحة «حالة قاعدة البيانات» في الإعدادات (فكرة كويسة) لكنها **للعرض فقط** من `/api/health`، بدون أي مدخلات.

**اختبار القبول:** `curl -X POST /api/db/connect` يرجع 404. لا يوجد أي حقل لإدخال رابط قاعدة بيانات في الواجهة. الرابط مش موجود في أي ملف في المشروع.

### الخطأ 4: تسريب الإعدادات والأسرار في ردود الـ API
**المكان:** `getFullData()` في `server.ts` (حوالي 215–250)، `GET /api/master-state` (حوالي 333)، `GET /api/data` (حوالي 438)، ومفتاح Gemini (`gemini_api_key` حوالي 65 و817).
**الحل:**
1. اكتب دالة `publicState()` ترجّع **فقط**: الأصناف، التصنيفات، الموردين، القوالب، الحركات (آخر N)، وإعدادات عامة غير حساسة (`default_min_threshold`). لا PIN، لا hash، لا مفاتيح، لا روابط.
2. مفتاح Gemini **من `process.env.GEMINI_API_KEY` فقط.** احذف `gemini_api_key` من الإعدادات، واحذف خانة `set-gemini-key` وزر `btn-save-gemini-key` من الواجهة (حوالي 1594–1597 و3755)، واحذف `req.body.apiKey` من نقطة الاستشارة.
3. وحّد النقطتين `GET /api/master-state` و`GET /api/data` في `GET /api/state` واحدة بنفس `publicState()`.

### الخطأ 5: أي حد يقدر يمسح أو يستبدل كل البيانات
**المكان:** `POST /api/master-state` (حوالي 342–395): بتستقبل حالة كاملة من أي متصفح بدون تحقق وتعمل `deleteMany` ثم `insertMany`.
**ليه ده خطر:** بدون دخول، أي حد يبعت `items: []` فيتمسح المخزون كله. وحتى مع حسن النية: جهازين متزامنين = آخر واحد يكتب يمسح شغل التاني. وكمان `deleteMany` ثم `insertMany` من غير معاملة معناها لو السيرفر وقع في النص تضيع البيانات.
**الحل:** **احذف النقطة دي بالكامل** (GET و POST). الواجهة تعمل عمليات محددة عبر نقاط الجزء 3، والسيرفر هو الوحيد اللي بيغيّر البيانات. واحذف دالة `saveStateAndSync` اللي بتبعت الحالة كلها (حوالي 2031–2060) واستبدلها بنظام الجزء 6.

### الخطأ 6: لا يوجد قفل حقيقي للمحاولات الخاطئة
**المكان:** `pinAttempts` في `index.html` (حوالي 2009 و3391): عدّاد في المتصفح بيتصفّر بإعادة تحميل الصفحة، ومفيش قفل أصلاً.
**الحل (في السيرفر):**
1. مجموعة/مستند `login_attempts` بمفتاح (IP). بعد **5 محاولات خاطئة خلال 15 دقيقة**: ارجع `429` مع `retry_after_seconds` وارفض حتى لو الـ PIN صح، لحد ما المدة تخلص.
2. كمان قفل عالمي على الحساب: بعد 10 محاولات فاشلة إجمالاً في ساعة، قفل 30 دقيقة.
3. زوّد `express-rate-limit` على `/api/auth/*` (10 طلبات/15 دقيقة/IP) وعلى `/api/ai/*` (10/ساعة).
4. الواجهة تعرض: «تم تجاوز عدد المحاولات، حاول بعد X دقيقة» من قيمة `retry_after_seconds` اللي السيرفر بيرجّعها، مش من عدّاد محلي.
5. سجّل (بدون الـ PIN) وقت وعنوان IP لكل محاولة فاشلة.

### الخطأ 7: ثغرة XSS (حقن نصوص) في الواجهة
**المكان:** حوالي 22 استخدام لـ `innerHTML` في `index.html`، وأهمها: `capGrid.innerHTML` (2282)، `urgentItemsCont.innerHTML` (2302)، `tbody.innerHTML` في الجداول (2359، 2444، 2569، 2614، 2689)، `container.innerHTML` للقوالب (2514)، وقوائم الاختيار (2837، 2842، 2950).
**ليه ده خطر:** لو حد كتب اسم صنف زي `<img src=x onerror="...">` فالكود بيتنفذ في متصفح كل مدير. ويقدر يسرق الجلسة أو يعدّل البيانات.
**الحل:**
1. اعمل دالة واحدة مركزية:
```js
const escapeHtml = (v) => String(v ?? '')
  .replace(/&/g,'&amp;').replace(/</g,'&lt;').replace(/>/g,'&gt;')
  .replace(/"/g,'&quot;').replace(/'/g,'&#39;');
```
2. كل قيمة نصية جاية من المستخدم أو من قاعدة البيانات (اسم الصنف، المواصفات، SKU، مكان التخزين، سبب الحركة، اسم القالب، اسم المورد، التصنيف) تتمرر عليها قبل ما تدخل في أي قالب HTML نصي. الأرقام تتحول بـ `Number()` أولاً.
3. القيم اللي بتدخل في خصائص مثل `data-id="..."` و`value="..."` كمان تتعمل لها escape.
4. الأفضل في الأماكن البسيطة استخدم `textContent` بدل `innerHTML`.
5. السيرفر كمان يرفض/ينظّف أي نص فيه `<` أو `>` في أسماء الأصناف (أو يقبله ويعتمد على escape في العرض: اختار واحد واكتبه في التقرير).
6. أضف رؤوس أمان بـ `helmet` وسياسة CSP تمنع inline scripts المجهولة (لو ممكن بعد نقل الـ JS لملف خارجي).

**اختبار القبول:** أضف صنف اسمه `<b>اختبار</b><img src=x onerror=alert(1)>`. لازم يظهر كنص حرفي في كل الشاشات، ومفيش alert.

## الجزء 4: أخطاء سلامة البيانات والمنطق (وكيفية إصلاحها)

### الخطأ 8: الصرف والتوريد مش ذريين (Race Condition)
**المكان:** `POST /api/movements` (حوالي 547–603): بيقرأ الرصيد ثم يحسب `item.quantity + changeAmount` ثم يكتب. لو شخصين صرفوا نفس الصنف في نفس اللحظة، واحد منهم بيضيع.
**الحل:** استخدم عملية ذرية مع شرط وداخل معاملة:
```ts
await session.withTransaction(async () => {
  const res = await items.findOneAndUpdate(
    { id: itemId, is_archived: { $ne: true }, ...(delta < 0 ? { quantity: { $gte: -delta } } : {}) },
    { $inc: { quantity: delta, version: 1 }, $set: { updated_at: now } },
    { returnDocument: 'after', session }
  );
  if (!res) throw new ApiError(400, 'الرصيد غير كافٍ أو الصنف غير موجود');
  await movements.insertOne({ /* before = res.quantity - delta, after = res.quantity */ }, { session });
});
```
(لاحظ إن `$inc` واحد بيزوّد الكمية والـ `version` معاً.) تأكد إن Atlas Cluster يدعم المعاملات (أي cluster مش مجاني M0 قديم؛ لو M0 بيدعمها كمان في الإصدارات الحديثة. لو لا، استخدم نمط `findOneAndUpdate` مع الشرط فقط وتسجيل الحركة بعده مع إعادة المحاولة).

### الخطأ 9: تنفيذ قالب الشغل مش «كله أو لا شيء»
**المكان:** `POST /api/job-templates/apply` (حوالي 726–792): بيتحقق من كل البنود ثم يخصم في حلقة. لو حصل خطأ في النص، يبقى خصم جزئي. وكمان لو صنف مكرر في بنود القالب، التحقق بيقارن كل بند لوحده فيعدي، والخصم الفعلي بيطلّع رصيد سالب.
**الحل:**
1. اجمع البنود حسب `item_id` أولاً (مجموع الكميات × المضاعف).
2. نفّذ كله داخل معاملة واحدة، كل صنف بنفس نمط الخطأ 8. أي فشل = `abortTransaction` ولا يتغير شيء.
3. رفض لو أي صنف مؤرشف أو محذوف، واذكر اسم الصنف والمطلوب والمتوفر بالعربي.
4. المضاعف: عدد صحيح من 1 إلى 1000.
5. كل الحركات الناتجة تشارك `reference_id` واحد (معرّف التنفيذ).
6. قرّب الكميات بـ `Math.round(x * 1000) / 1000` لتفادي أخطاء الفاصلة العائمة (مثل `0.1 × 3`).
